## Long Messages On Google Free (fixed 2026-08-20, PTB observation owed)

The first long-message patch split on JavaScript string length, but Google Free carries `q` in the URL and CJK expands heavily under `encodeURIComponent`; a 1,600-character CJK chunk could still produce an oversized request. The splitter now budgets the encoded `q` length, preserves paragraph/sentence boundaries where possible, hard-splits by Unicode code point only as a last resort, and concatenates to the exact input. Requests remain sequential and the caller receives a result only after every chunk succeeds. Tests drive the real adapter through multiple CJK requests and verify encoded bounds, lossless input, combined output, and first-chunk language detection.

**Field correction 2026-08-20:** the screenshot's 1,884-character English failure was NOT an HTTP-length failure. The Google adapter now converts only canonical protection markers to wire-only `__DTA_N__` tokens and reverses them before validation. The same live reproduction returned 200/200/200 with all 10 protected segments present. Hard chunk cuts treat both marker forms as indivisible. The strict shared guard remains unchanged.

## Architecture Finding (2026-08-19): One Root, Three Symptoms

The user's three standing complaints - scrollbar bouncing during auto-translate, capsule position glitches, composer icon flicker - are all downstream of ONE architectural fact: every display transaction repaints by rebuilding the whole chat layer (LayerProvider children nulled and restored), because mounted message rows are memoized and no per-row invalidation is known to work on this client (forceUpdate measured no-op, 2026-08-13). The rebuild unmounts the composer (icon flicker), unmounts the capsule's anchor and the hint strip (capsule glitches), and destroys scroll state that then needs restoring (bounce). Fix history on codex/capsule-counter:

- Icon flicker: atomic single-task rebuild (flushSync blank+restore, no paintable blank frame), fallback to rerenderAll. Settings panel now shows `repaint NA/MF` (atomic/fallback counts) next to the build id so a user screenshot proves which path runs. FIRST FIELD READING (2026-08-19 screenshot): `repaint 0A/56F` - the atomic path never engaged, because the runtime wired a REDUCED BDFDB surface (dotCN + MessageUtils only) into the display runtime and ReactUtils.flushSync was always undefined. Fixed the same day: the wiring now carries ReactUtils/ObjectUtils/LibraryStores/DMUtils/ChannelUtils (pinned by a wiring regression test), and the atomic module additionally resolves flushSync through BdApi.Webpack.getByKeys("flushSync","createPortal") if BDFDB's ReactDOM module lacks it. Watch the NEXT screenshot: A should be climbing; if it is still 0, flushSync is genuinely absent on this client and the per-row endgame moves up.
- Capsule fallback band: the 26px hint-strip clearance shipped in the morning was REJECTED by the user in the afternoon (screenshot: the pill floating over message content read as worse drift; "we had a working position"). The fallback returned to hugging the input at 8px. Overlap with a real slow-mode strip is owned by detection (walk + false-positive rejection), not by fallback distance.
- Scroll bounce: there were FOUR scroll writers per transaction (viewport capture, the rebuild's own raw scrollTop restore, Discord's remount behavior, the viewport anchor restore two frames later). Raw pixel restore disagrees with the anchor restore whenever translated rows change heights - the visible per-transaction bounce. Scroll ownership is now the viewport store ALONE: the atomic rebuild writes no scroll, the anchor restore runs synchronously in the rebuild's task (first painted frame correct), and the deferred restore remains as a >=1px late-drift corrector.
- Capsule: stale-hint zero-rect guard, lost-anchor keep-last-position, strip-clearance fallback band, zombie-instance gate, and the hint scan structurally rejecting nodes inside the message list (translated messages contain 已开启/slow mode as ordinary text and sat exactly in the proximity band - 2026-08-19 screenshot).

## Cadence Audit (2026-08-19 late): the rebuild count is set upstream, and scroll-back historical batching is broken

Supersedes the first night-audit blame ("the one-by-one repaints come from the live lane, unavoidable") - that was only part of the truth. The user's memory is correct: the DESIGNED historical behavior is collect-whole-snapshot -> one atomic commit -> one rebuild, and it still works that way for the enable-time scan (the 62-item job; chunks of 10 tick only the capsule). What breaks it is SCROLL-BACK:

- `resolveLoadedMessageContentTranslation` (translation-display-logic.js:299) queues every mounted untranslated row; `queueMessage` routes `historicalLoad` items to `collectHistoricalTranslationMessage` (live-translation-queue.js:219 -> runtime.js:1961).
- Collect seals via `scheduleHistoricalTranslationJobStart` on a MICROTASK (runtime.js:1976-1988): the job window is one render tick. Rows mounting across scroll ticks therefore land in MICRO-JOBS of 2-5 messages; jobs queue behind `runningPromise` and run sequentially, each with its own atomic commit -> its own whole-layer rebuild, seconds apart. That is the user-visible "one-by-one historical translation, icon blinks each time".
- Cached rows misclassified as live (`isLikelyLiveAutoTranslateMessage`) commit per item through `handleCachedItem` - the cached-replay wave, same per-transaction rebuild.
- Genuinely new live messages: one transaction each by nature (120ms window cannot merge arrivals seconds apart); bursts within one tick already share one AI request (LIVE_AI_BATCH_ITEM_LIMIT 10).

**Why three fixes in a row failed (recorded as a working rule):** all three (atomic flushSync rebuild, per-row forceUpdate registry, primitive swap-back) changed HOW a rebuild happens, never HOW MANY - and the count is set by the upstream arrival cadence audited above, which no one had traced end-to-end. Each also bet on unverifiable client internals (flushSync availability, class instances) that only field-tested false. Rule: before touching the display primitive again, attribute the trigger; five sources (live commit, cached replay, historical job commit, bounded retry, lifecycle path B) share one symptom.

**Phased plan (agreed direction 2026-08-19 night; 0 and 1 SHIPPED the same night):**

- **Phase 0 SHIPPED (`c97021b`):** every flush carries its trigger lane (live/cached/historical/manual/retry, threaded scheduler -> display runtime -> controller -> adapter), the adapter books rebuilds per lane plus a 40-entry recent-rebuild ring, path-B lifecycle full repaints are counted in the scheduler, and the settings note reads e.g. `repaint 0L/12R (hist 8, live 3) · full 2`. Pinned across repaint-scheduler / adapter / controller / live-queue / refresh-wiring tests.
- **Phase 1a SHIPPED (`553da4f`, policy module `src/orchestrator/historical-snapshot-cadence.js`):** the per-tick microtask seal is gone. A collecting snapshot seals after a 500ms quiet window (HISTORICAL_COLLECT_QUIET_MS), an active scroll keeps the window open until the user idles, rows collected while a job ran seal at job end when idle (preserving the live-handoff decision point - the handoff contract tests all pass unchanged), and batches sealed behind a running job MERGE into one before starting (job.absorb, loaded limit still bounds size, queue markers repointed). Result: a scroll-back session = one job = one atomic commit = one whole-layer rebuild. Pinned by three new tests in historical-translation-job.test.js.
- **Phase 1b assessed, no change needed:** processQueue drains cached items back-to-back in one tick, so their flushes land inside one 120ms scheduler window - one rebuild per replay wave already. The cache lane counter from Phase 0 verifies this in the field.

## Next Phase: Display System Unification

The modular extraction created modules around a retained god object: `src/legacy/runtime.js` is still the composition root, Discord patch shell, UI coordinator, status DOM owner, and lifecycle dispatcher, directly importing most source modules, and the generated artifact exceeds the documented size guardrails.

**Strategy (decided 2026-08-16, branch `codex/display-unification`): drain the legacy runtime bottom-up by ownership instead of rewriting the composition root top-down.** The runtime is 4,322 lines: a 157-line factory closure (2 shared vars) plus 443 class methods averaging under 10 lines (largest: `translateMessage` 176, `translateText` 128, `onLoad` 85), so a big-bang composition-root rewrite carries uncontrollable risk while per-ownership extraction fits the existing ratchet. The small composition root emerges at the end, when the drained shell is thin enough to replace.
